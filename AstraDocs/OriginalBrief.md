# iPhone Dash Cam App — Astra Handover Brief

## Objective

Design and build a native iPhone dash-cam application that can be mounted in a vehicle and continuously record video while maintaining a rolling buffer of approximately the **last 5 minutes**.

The app should prioritize reliability, low-friction operation, sensible thermal/storage management, and preservation of footage when an incident occurs.

Before implementation, **review this brief, validate the proposed architecture against current iOS APIs/restrictions, identify incorrect assumptions, and propose improvements.** Then create a staged implementation and testing plan.

## Initial Platform

Start with **iPhone/iOS only**.

Preferred stack:

- **Swift**
- **SwiftUI** for UI
- **AVFoundation** for camera capture/video pipeline
- Apple's hardware-supported video encoding where appropriate
- **Core Location** for optional GPS/speed/location metadata
- **Core Motion** only if supplementary motion-based incident detection is useful
- **SafetyKit / Apple's crash-related APIs**, if currently available to third-party apps for this use case

Do not assume SafetyKit access is available. Verify the current Apple documentation, supported devices/OS versions, entitlement/permission requirements, App Store restrictions, and exactly what crash information/events a third-party application can receive.

## Core Recording Architecture

Do not record one indefinitely growing video file.

Implement a segmented circular recording system, for example:

1. Continuously capture camera video.
2. Encode and write short video segments to temporary storage.
3. Maintain enough segments to represent approximately the previous 5 minutes.
4. Automatically delete/overwrite the oldest unprotected segments.
5. When an incident is triggered, immediately protect the relevant buffered footage from deletion.
6. Continue recording for a configurable period after the incident so the saved clip includes both **pre-event and post-event footage**.
7. Combine/export the relevant segments into an incident recording when appropriate.

Design this so an unexpected app termination or interruption minimizes the amount of footage lost.

## Incident Detection

Use a layered approach.

### 1. Apple-native crash detection

Investigate whether Apple's current **SafetyKit** APIs allow an eligible third-party app to receive severe vehicle crash events generated by Apple's Crash Detection system.

If available and appropriate:

- Determine required entitlements and Apple's approval process.
- Determine supported iPhone models and minimum iOS version.
- Determine whether the app must be foregrounded/running.
- Determine callback/event behavior and latency.
- Determine what data Apple exposes.
- Determine whether relying on this mechanism is appropriate for a consumer dash-cam application.

When an Apple crash event is received, trigger the same internal incident-saving pipeline used by every other trigger.

### 2. Manual incident trigger

Provide a large, obvious **Save Incident** control.

This should immediately protect the previous buffered footage and continue recording the configured post-event period.

### 3. Optional supplementary detection

Investigate whether Core Motion accelerometer/gyroscope data can provide useful supplementary detection for:

- sudden deceleration
- strong impact
- unusual rotational movement

Do not make this the primary mechanism until false-positive and false-negative behavior has been tested extensively.

## Unified Incident Pipeline

All incident sources should call the same internal event handler, conceptually:

`triggerIncident(source:)`

Possible sources:

- Apple Crash Detection / SafetyKit
- manual button
- motion heuristic
- developer/test trigger

The recording/buffering system should not care which source generated the incident.

## Testing Architecture

Incident detection must be testable **without crashing a vehicle or deliberately creating dangerous driving conditions**.

Build testing hooks from the beginning.

Include:

- A developer-only **Simulate Crash** control that invokes the real incident pipeline.
- Ability to inject prerecorded/synthetic accelerometer and gyroscope traces into any custom motion detector.
- Unit tests for circular-buffer retention/deletion logic.
- Tests verifying pre-event and post-event footage are preserved correctly.
- Tests for camera interruptions, phone calls/system interruptions, low storage, thermal pressure, permission changes, app termination, and restart/recovery.
- Long-duration recording tests on physical iPhones.
- Normal-road driving tests focused on false positives from potholes, hard braking, phone-mount vibration, speed bumps, etc.

If SafetyKit supports a sandbox/test mechanism for crash events, investigate and use Apple's supported mechanism rather than attempting to generate a real crash event.

## MVP / V0.1

The first usable build should remain deliberately small.

Required:

- Rear-camera preview
- Start/stop dash-cam session
- Continuous segmented recording
- ~5-minute rolling buffer
- Automatic deletion of expired segments
- Manual **Save Incident** button
- Preserve footage from before and after an incident
- Saved-clips library
- Basic storage management
- Clear camera/microphone permission handling
- Developer **Simulate Crash** function
- Robust error logging

SafetyKit integration can enter V0.1 if access is straightforward; otherwise architect the incident interface now and add SafetyKit once entitlement/API requirements are resolved.

## Later Features

Do not allow these to delay the MVP:

- GPS route metadata
- vehicle speed overlay
- timestamp/location overlay
- configurable buffer length
- configurable post-incident recording duration
- front/rear camera options
- automatic crash detection
- background/locked-screen behavior where iOS permits it
- emergency contact workflow
- cloud backup
- automatic upload of protected clips
- CarPlay-related features, if relevant and permitted
- Android version

## Key Engineering Risks to Investigate Early

Spend time validating these before polishing UI:

1. iOS behavior when the device locks or the app backgrounds.
2. Camera-session interruptions.
3. Thermal behavior during prolonged recording.
4. Battery drain while recording/charging in a vehicle.
5. Storage pressure and safe cleanup.
6. File integrity after unexpected termination.
7. AVFoundation behavior over multi-hour sessions.
8. Camera stabilization and mount vibration.
9. Audio-session interruptions.
10. SafetyKit eligibility and entitlement approval.
11. Whether Apple's crash detection can reliably trigger the application's desired workflow.
12. App Store policy/privacy requirements for continuous video, location, and crash-related functionality.

## Architecture Expectations

Keep components modular. Suggested separation:

- `CameraCaptureService`
- `SegmentRecorder`
- `RollingBufferManager`
- `IncidentManager`
- `IncidentDetector` protocol
- `SafetyKitIncidentDetector`
- `MotionIncidentDetector`
- `ManualIncidentDetector`
- `ClipExportService`
- `StorageManager`
- `LocationService`
- `AppLogger`

Avoid tightly coupling crash detection to AVFoundation recording logic.

## Astra Instructions

Please:

1. **Review and challenge this specification before coding.**
2. Check current Apple developer documentation for AVFoundation, SafetyKit, Core Motion, background execution, and relevant entitlements.
3. Explicitly flag anything in this brief that current iOS APIs do not permit.
4. Propose the final architecture.
5. Produce a phased implementation plan with clear milestones.
6. Identify what can be tested in Simulator versus what requires a physical iPhone.
7. Build the smallest functional vertical slice first.
8. Compile and test after each meaningful milestone.
9. Add automated tests wherever practical.
10. Do not silently work around platform restrictions; document them.
11. Keep a changelog and use semantic versioning (e.g. `0.1.0`, `0.1.1`).
12. Prioritize reliability of recording and footage preservation over UI polish.

### Definition of Success for First Milestone

On a physical iPhone mounted in a vehicle, the app can record continuously for an extended test drive, retain only the configured rolling window during normal operation, and—when the test/manual incident trigger fires—reliably preserve the footage immediately before and after that event.

Once that works reliably, proceed to native crash-event integration and supplementary automatic detection.
