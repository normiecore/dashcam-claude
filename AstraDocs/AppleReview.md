# Apple platform review

Reviewed 29 September 2026 against Apple's documentation. This document distinguishes documented capability from engineering decisions and unverified behavior. It supersedes conflicting assumptions in the supplied brief.

| Area | Finding | V0.1 decision |
|---|---|---|
| SafetyKit availability | Real public APIs exist from iOS 16. `SACrashDetectionManager.isAvailable` is the runtime authority; OS version alone is insufficient. Apple's overview names the first supporting iPhone 14 and Watch generations, not an exhaustive future-device list. | Define a common incident source, but do not link or request SafetyKit in this build. |
| SafetyKit access | Requires Apple's restricted `com.apple.developer.severe-vehicular-crash-event` entitlement plus user authorization. Only one designated app receives events. An ordinary dashcam is not automatically eligible. Apple's application form requires developer sign-in; eligibility/approval remains unresolved. | Manual saving is the dependable app-controlled trigger. No claim of automatic collision detection. |
| Event behavior | Events expose date, location and emergency-response information, not raw Apple's sensor/classifier internals. A background launch can deliver an event; repeated delivery and only the latest of multiple pending events are documented. No guaranteed callback latency was found in the reviewed public documentation. | Future adapter must deduplicate by event date, reconcile historical event time with capture sessions, and protect already-recorded files. Never assume callback time equals crash time or promise a complete pre-event window for delayed events. |
| Apple simulation | Apple explicitly recommends iOS Simulator for SafetyKit event/background testing. This is distinct from injecting the app's own incident handler. | Debug Simulate Crash tests the app pipeline only. Once entitlement access is confirmed, use the installed Simulator's documented Crash Detection event facility; exact controls require verification in that Xcode version. No invented public injection API or real-world collision tests. |
| Background camera | Standard backgrounding can interrupt camera access. Multitasking exceptions exist. The old multitasking-camera entitlement is deprecated from iOS 18; support must be queried and qualifying environments include particular iPad/multitasking and VoIP cases. This is not general authorization for a background iPhone dashcam. | Foreground/unlocked recording. No fake VoIP, audio, PiP, or location mode to keep capture alive. Background task time is only for finishing writes. |
| Lock and suspension | A background execution extension is finite and may expire or be terminated early. It does not grant camera access or guaranteed post-event footage. | Disable auto-lock while recording; manual lock/background stops capture and labels incomplete tails. Explicit restart after return. |
| AVFoundation | `AVCaptureMovieFileOutput` stop/start rotations do not promise gapless video. Sample-buffer outputs with separate `AVAssetWriter`s allow one capture session to remain active through file rotation. | Serial sample ingestion, bounded writer finishing, 10-second MOV files. This reduces avoidable gaps; it is not yet evidence of gap-free behavior. |
| Termination | `AVAssetWriter.movieFragmentInterval` is disabled by default; MOV fragments can make partially written media readable. Finalization and storage hardware still matter. | One-second initial/subsequent fragments. Register writers before opening files. Preserve unfinished files for recovery; do not assume every fragment is repairable. Automatic remux/repair is deferred. |
| Storage | Temporary and cache storage may be purged. Application Support is appropriate for persistent private media; backup exclusion is explicit. | Original media and manifest live in Application Support. Export derivatives use Caches. Originals remain until safe rolling cleanup or explicit incident deletion. No cloud backup. |
| Data protection | `completeUntilFirstUserAuthentication` permits access after the first unlock, including after a later lock. It is a privacy/availability tradeoff, not a camera permission. | Apply this class to storage so an in-flight finalization can complete on lock. Device-first-unlock restrictions still apply. |
| Privacy | Camera/microphone purpose strings and user consent are required. Disk capacity is a required-reason API; E174.1 covers visible behavior for insufficient storage. App Review requires clear recording indication. | Camera permission on start; microphone opt-in; visible recording state; bundled privacy manifest. No location/motion permission or network upload. App Store submission still needs its own privacy/review check. |
| Core Motion | Raw acceleration includes gravity; device motion separates gravity/user acceleration. Mount orientation and vibration materially affect heuristic signals. This is not equivalent to Apple's Crash Detection. | No automatic motion detector in V0.1. Trace replay becomes required if a detector is added, before any public automatic-detection claim. |
| Physical testing | Simulator does not reproduce a real iPhone's camera, encoder, thermal, storage, battery, or interruption behavior. | XCTest synthetic video and logic tests are useful; mounted physical-device qualification is a separate mandatory gate. |

## Engineering implications

The five-minute buffer is a retention target, not a promise that five minutes exists just after start or following a gap. At 4 Mbps, five minutes of video is approximately 150 MB before audio/container overhead (4,000,000 × 300 ÷ 8). Protected incidents can grow storage without bound until the user deletes them; recording stops at the reserve rather than removing incident footage. Excluding the originals from backup is deliberate in this first local-only build: the interface and README must make export responsibility clear.

Time intervals use the capture host clock, scoped by recording-session UUID. Wall-clock labels can change independently. A later SafetyKit adapter must not compare an Apple event's Date directly with these monotonic values, particularly across reboot. It needs a durable clock mapping and a delayed-event retention policy.
